# Memory Consolidation Skill

## 🎯 技能定位

模拟人类睡眠巩固记忆的过程，定期整理 `.workbuddy/memory/` 目录：
- 将分散的日常日志提炼为结构化长期记忆
- 压缩冗余信息，控制 MEMORY.md 在合理大小
- 建立跨会话的知识连接

---

## 📂 记忆系统结构

```
.workbuddy/memory/
├── MEMORY.md            # 长期记忆（精华提炼，按项目分区）
├── 2026-04-16.md        # 今日工作日志
├── 2026-04-15.md        # 昨日工作日志
└── ...                  # 更早的日志（30天以上可归档）
```

---

## 🏗️ MEMORY.md 分区结构（v2.0 核心）

MEMORY.md 采用 **项目隔离分区** 设计，防止跨项目知识污染：

```markdown
# MEMORY.md

## 🔧 通用偏好（跨项目有效）
- [0.9] 语言：中文为主，技术术语保留英文
- [0.9] 风格：简洁直接，不要冗余寒暄
- [0.7] 输出：优先 Markdown 表格

## 📁 项目：{项目名}
- **技术栈**：{语言/框架}
- **状态**：进行中 / 已完成 / 暂停
- **关键约束**：{项目特定约束}
- **编码偏好**：{项目特定编码风格}
- **踩坑经验**：{项目特定经验}

## 📁 项目：{另一个项目}
- ...
````

### 分区规则

| 规则 | 说明 |
|------|------|
| **通用偏好** | 用户明确声明的跨项目偏好，始终加载 |
| **项目分区** | 按工作区路径或用户声明的项目名分组，仅加载当前项目相关 |
| **新增项目** | 当日志中出现 3 次以上同一项目相关条目时，自动创建新分区 |
| **合并判断** | 如果两个项目名相似度 > 80%（如"保险系统"和"保险产品"），提示用户确认是否合并 |

### 读取策略（v2.1 借鉴 Hermes 按需检索）

**原则：从全量读取过渡到智能按需加载，降低 token 消耗**

1. **始终加载**：通用偏好区 + 当前项目分区
2. **按需加载**：通过工作区路径匹配当前项目分区
3. **不加载**：其他项目分区（减少无关信息干扰）
4. **关键词预检**（新增）：会话开始时，先扫描 MEMORY.md 的标题行和关键词，
   仅加载与当前任务相关的分区（而非全量读取所有项目分区）
5. **记忆摘要**（借鉴 Hermes FTS5 + LLM 摘要）：
   - 当 MEMORY.md > 50KB 时，触发摘要压缩
   - 将 [0.3] 置信度的试探性条目压缩为一行摘要
   - 保留 [0.7]+ 置信度条目的完整内容

### 记忆索引系统（v2.2 新增 - 模拟 Hermes FTS5 语义检索）

> **问题**：MEMORY.md 全量读取浪费 token，关键词预检不够智能。
> **方案**：维护一个轻量级 JSON 索引文件，实现按主题快速定位。

#### 索引使用流程

```
会话开始
    ↓
读取 memory-index.json（~1KB，极低成本）
    ↓
匹配当前任务关键词与索引 keywords
    ↓
选择需要加载的 MEMORY.md 分区：
    ├── always_load: true → 始终加载
    ├── workspace_match 命中 → 加载（当前工作区路径匹配）
    ├── keywords ≥ 2 个命中 → 加载
    └── 其他 → 跳过
    ↓
用 read_file(path, offset, limit) 精准读取选定分区
```

#### 索引维护规则

| 触发时机 | 维护动作 |
|---------|---------|
| 每次更新 MEMORY.md 后 | 同步更新索引中对应分区的 line_start/line_end |
| 新增项目分区时 | 在索引中添加新 section |
| 删除/压缩条目时 | 更新索引的 line 范围 |
| 跨会话模式变化时 | 更新 cross_session_patterns |
| memory-consolidation 整理后 | 全量重建索引 |

#### 索引的局限（诚实标注）

- 这是**关键词匹配**，不是真正的语义检索（向量嵌入）
- 如果用户的表述与索引关键词不重叠，可能漏加载
- 补救：执行中发现需要额外记忆时，中途补充读取
- 理想方案：平台支持 SQLite FTS5 或向量检索

## 📋 四阶段工作流程

### Phase 1 · Orient（定位）
```
1. read_file 读取 MEMORY.md（了解现有长期记忆）
2. list_dir 扫描 memory/ 目录（获取所有日志文件）
3. 确定整理范围（距上次整理的新增日志）
4. 统计当前记忆健康状态
```

### Phase 2 · Gather（收集）
```
1. 按日期顺序读取未处理的日志文件
2. 提取关键信息：
   - 用户偏好和习惯
   - 项目进展和决策
   - 遇到的问题和解决方案
   - 经验教训和模式
3. 标记高价值内容（用户明确说"记住"的）
```

### Phase 3 · Consolidate（整合）
```
1. 按主题归类新记忆
2. 识别新记忆所属项目（通过工作区路径、文件路径、上下文关键词判断）
3. 分配置信度评分（参考下方"置信度评估规则"）
4. 将记忆写入对应项目分区（而非统一堆放）
5. 与 MEMORY.md 中现有内容对比，合并相关条目
6. 更新已变化的信息
7. 建立记忆连接（不同主题间的关联）
```

### 置信度评估规则

| 分数 | 含义 | 触发条件 |
|------|------|---------|
| **[0.3]** | 试探性 | 用户提及 1 次，未明确要求记住 |
| **[0.5]** | 有倾向 | 用户提及 2-3 次，或主动选择但未强调 |
| **[0.7]** | 偏好确认 | 用户明确表达偏好，或多次遵循同一模式 |
| **[0.9]** | 核心习惯 | 用户明确说"记住这个"，或 5+ 次重复确认 |

**晋升规则**：每次整理时，[0.3] 出现第 2 次升为 [0.5]，[0.5] 出现第 4 次升为 [0.7]，[0.7] 被用户明确确认后升为 [0.9]。

**降级规则**：如果 [0.7] 或 [0.9] 的条目在最近 30 天内未被引用或遵循，降一级。

### Phase 4 · Prune（修剪）
```
1. 删除明确过期的临时信息
2. 压缩冗余日志（30天以上 → 归档到 MEMORY.md）
3. 删除已归档的日志文件（可选，需用户确认）
4. 报告整理结果
```

### Phase 5 · Rebuild Index（索引重建）（v2.3 新增）

> **问题**：MEMORY.md 每次更新都会导致行号偏移，但 memory-index.json 的 sections.line_start/line_end
> 不会自动更新。随着时间推移，索引的行号越来越不准确，导致按需读取定位偏差。
> **方案**：每次 memory-consolidation 整理完成后，全量重建索引。

**重建流程**：

```
Phase 3/4 完成，MEMORY.md 已更新
    ↓
Step 1: 读取 MEMORY.md 全文
    ↓
Step 2: 扫描所有 ## 标题行，提取分区信息
    │
    │ 对每个 ## 标题行：
    │   - 记录行号（line_start）
    │   - 找到下一个 ## 标题行的行号 - 1（line_end）
    │   - 提取关键词（从该分区的条目中提取非停用词）
    │   - 检查 always_load（"通用偏好" = true）
    │   - 检查 workspace_match（从标题和内容推断）
    ↓
Step 3: 对比现有索引
    │
    │ 检测以下变化：
    │ - 新增分区（MEMORY.md 有，索引无）→ 添加
    │ - 删除分区（MEMORY.md 无，索引有）→ 移除
    │ - 行号偏移（line_start/line_end 不匹配）→ 更新
    │ - 关键词变化 → 更新
    ↓
Step 4: 更新 memory-index.json
    - version + 0.1
    - last_updated = 今天日期
    - memory_file_size_kb = 实际文件大小
    - sections = 重建后的数组
    ↓
Step 5: 验证索引完整性
    - 每个 section 的 line_start < line_end
    - 所有 section 的 line_start 按升序排列
    - 无重复 id
    - 至少有一个 always_load: true 的 section
```

### Phase 6 · Audit Trail（审计轨迹）（v2.4 新增）

> **问题**：自进化系统的执行是否真的被遵循了？目前没有记录。
> 比如上一轮审计记录了"需修正版本号"，下一轮是否真的修正了？
> **方案**：每次 memory-consolidation 整理完成后，记录执行摘要到 audit_history。

**记录内容**：

```json
{
  "date": "YYYY-MM-DD",
  "trigger": "手动触发 / 定期整理 / v{版本}初始化",
  "actions": [
    {"type": "consolidation", "summary": "归档了 3 个日志文件，提炼 12 条长期记忆"},
    {"type": "prune", "summary": "删除 2 条过期信息，压缩 1 条冗余"}
  ],
  "memory_file_size_kb": 3,
  "log_files_processed": 5,
  "index_rebuilt": true,
  "registry_synced": true,
  "quality_score": null
}
```

**与 memory-index.json 的协同**：

audit_history 数组追加到 memory-index.json，每次整理后：
- 如果 self-improvement 在本轮也执行了反思 → quality_score 填入评分
- 如果 skill-evolution 在本轮也执行了审计 → 追加 skill_evolution 审计摘要
- 如果 workflow-loop 的联动验证也执行了 → linkage_verified 标记为 true

**审计轨迹的用途**：

| 用途 | 怎么用 |
|------|--------|
| 验证规则遵循度 | 检查 audit_history 中"应做"和"实际做"的差异 |
| 识别僵尸规则 | 某规则连续 5 次审计都未执行 → 标记为低效规则 |
| 质量趋势 | quality_score 的时间序列反映进化效果 |

## ✅ 保留 vs ❌ 丢弃原则

### ✅ 应该保留
- 用户明确说"记住这个"、"记下来"的内容
- 重复出现（≥2次）的偏好或模式
- 影响未来决策的技术选型
- 项目重要里程碑和关键决策
- 踩过的坑和解决方案

### ❌ 应该丢弃
- 一次性任务的中间过程细节
- 临时搜索结果（非结论性的）
- 重复的日常操作记录
- 超过30天且未被引用的日志条目
- 过于琐碎的交互（如"帮我改个标点"）

## ⚙️ 核心规则

1. **最小权限**：整理时默认不删除文件，只在用户确认后删除
2. **保留原文**：归档时保留原始日志内容，只是移动而非重写
3. **透明操作**：每次整理都生成变更报告
4. **不过度概括**：提炼时保留足够细节，避免信息损失
5. **版本标注**：MEMORY.md 的重大更新注明更新日期和原因
6. **项目隔离**：项目 A 的记忆不影响项目 B 的判断，加载时按工作区路径匹配
7. **置信度驱动**：所有偏好条目必须带置信度前缀 [0.3]-[0.9]，渐进信任

## 🔍 Search Before Building（强制步骤）

在开始整理记忆前，执行三层搜索检查：

**Layer 1 - 项目内搜索**：
```bash
# 检查当前记忆状态
cat .workbuddy/memory/MEMORY.md 2>/dev/null | wc -l
# 检查有多少未处理的日志
ls -la .workbuddy/memory/*.md 2>/dev/null | wc -l
# 检查上次整理是什么时候
grep -i "整理时间\|最后更新" .workbuddy/memory/MEMORY.md 2>/dev/null | tail -5
```

**Layer 2 - 查找现有方案**：
- 检查是否有现有的记忆分类模板
- 检查 skill-evolution 是否有相关建议
- 查看其他 skill 是否有需要沉淀到记忆中的经验

**Layer 3 - 如无现有方案**：
- 确定本次整理的优先级（日志太多优先归档，MEMORY.md太大优先精简）
- 设计新的分区结构（如有必要）
- 确定需要保留的核心条目

## 🚨 Escalation Rules（升级机制）

**必须立即 STOP 并升级的情况**：

| 触发条件 | 处理方式 |
|---------|---------|
| 发现疑似敏感/隐私信息 | STOP，报告位置，要求用户确认处理方式 |
| 日志文件损坏或无法读取 | STOP，跳过该文件，记录问题 |
| 删除操作未获用户确认 | STOP，默认只归档不删除 |
| 3次整理尝试均失败 | STOP，报告失败原因 |
| MEMORY.md 格式损坏 | STOP，要求用户手动修复或备份 |

**Escalation 格式**：
```markdown
STATUS: BLOCKED
REASON: [问题描述]
AFFECTED_FILE: [受影响的文件]
ATTEMPTED: [尝试了什么]
RECOMMENDATION: [建议用户做什么]
```

## 📦 Workflow Loop（工作流闭环）

### 上游：定时触发 / 手动触发

| 上游场景 | 触发时机 |
|---------|---------|
| 周期性整理 | 建议每周一次，或 MEMORY.md > 100KB |
| 用户要求 | 用户说"整理记忆"、"清理日志" |
| 日志文件过多 | memory/ 目录下 > 30 个日志文件 |
| strategic-compact 触发 | 上下文压缩后需要整理压缩产生的结论 |

### 下游：整理完成后

| 下游 skill | 联动方式 |
|-----------|---------|
| `self-improvement` | 记录记忆整理的踩坑经验 |
| `workflow-loop` | 如果需要启动新工作流，提供上下文 |
| `skill-evolution` | 如果发现 skill 需要更新，触发 skill-evolution |

### 记忆整理标准闭环
```
定时/手动触发 → memory-consolidation 扫描 → 提取精华 → 更新 MEMORY.md
                    ↓                              ↓
              归档日志文件                  self-improvement 自检
                    ↓                              ↓
              生成整理报告 ──────────────→ skill-evolution（可选）
```

### 定期维护路径
```
用户会话 → self-improvement 自检 → 发现记忆问题 → memory-consolidation
                    ↓                              ↓
              skill-evolution ←── 多次发现同类问题 ──┘
```

## ✅ Completion Protocol（完成状态协议）

| 状态 | 含义 | 场景 |
|------|------|------|
| **DONE** | 整理成功完成 | 成功归档日志、更新 MEMORY.md |
| **DONE_WITH_CONCERNS** | 完成但有警告 | 部分日志无法处理/部分记忆待确认 |

## 🔄 触发词自进化规则

当用户输入某种表述但本 Skill 未被自动激活时，完成任务后**必须**执行：
1. 分析用户原始请求中的关键表述
2. 将其抽象为通用触发词（避免过于具体的个例）
3. 用 replace_in_file 工具将触发词追加到本文件 YAML frontmatter `description` 字段末尾
4. 不得重复添加已存在的触发词
