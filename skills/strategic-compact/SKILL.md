# Strategic Compact — 阶段感知上下文压缩

## 💰 Token 预算管理（v1.1 新增）

> **核心理念**：对工具调用次数和上下文消耗保持成本意识，避免低效路径浪费上下文空间。

### 任务预算估算（任务开始时快速评估）

| 任务类型 | 预估工具调用 | 预估预算 | 典型场景 |
|---------|------------|---------|---------|
| **简单查询** | 1-3 次 | 3,000 tokens | 查数据、读单个文件、简单问答 |
| **中等任务** | 4-8 次 | 10,000 tokens | 修改几个文件、小型功能、格式转换 |
| **复杂任务** | 9-15 次 | 20,000 tokens | 新功能开发、多文件重构、深度调研 |
| **超大型任务** | 16+ 次 | 30,000 tokens | 全栈开发、架构设计、系统集成 |

### 预算监控规则

```
任务执行中，持续监控效率：

🟢 健康：工具调用次数 / 预期完成度 ≥ 0.7
   → 继续执行

🟡 预警：工具调用次数超过预算 70%，但任务完成度 < 50%
   → 触发路径反思：
     1. 当前方法是不是走偏了？
     2. 有没有更直接的工具/方法？
     3. 是否应该换一个 Skill？

🔴 超支：同一子任务重试 ≥ 3 次仍未成功
   → 立即 STOP
   → 不再继续试错
   → 换方法 / 升级给用户 / 使用 find-skills 寻找替代方案
```

### 成本优化策略

| 策略 | 说明 | 示例 |
|------|------|------|
| **精准读取** | 用 limit/offset 参数只读需要的部分 | `read_file(path, offset=100, limit=50)` 而非全文件 |
| **精准搜索** | 用更具体的 pattern 减少无关结果 | `search_content(pattern="class.*Controller")` 而非泛搜索 |
| **避免重复读取** | 同一文件不读两次 | 缓存已读文件内容，后续从上下文引用 |
| **并行合并** | 无依赖的调用一次并行发出 | 见 workflow-loop 的并行优化规则 |
| **子智能体卸载** | 大量文件探索用 code-explorer 子智能体 | 避免在主上下文中读取 20+ 文件 |
| **快速失败** | 方法行不通时 3 次内换路 | 不在同一方向上浪费 5+ 次调用 |

### 预算报告（复杂任务完成后可选输出）

```markdown
## 执行效率报告

**任务**：{任务描述}
**实际工具调用**：{N} 次（预算 {M} 次）
**效率评分**：{完成度 / 调用次数} = {X}（> 0.7 为健康）

**优化建议**：
- {如有低效步骤，指出具体哪步可以优化}
```

## 📡 上下文压力感知（v1.2 新增）

> **借鉴 Hermes 的执行环境监控**：Hermes 能感知自身运行环境的内存/CPU 状态，
> WorkBuddy Agent 无法直接感知系统资源，但可以**间接推断上下文压力**。

### 压力信号识别

我无法直接获取 token 计数，但可以通过以下**代理指标**推断上下文压力：

| 压力级别 | 代理指标 | 说明 |
|---------|---------|------|
| 🟢 低 | 工具调用 < 5 次，Skill 未加载 | 上下文充裕 |
| 🟡 中 | 工具调用 5-12 次，1-2 个 Skill 已加载 | 开始有压力 |
| 🟠 高 | 工具调用 12-20 次，2+ Skill 已加载，大型文件读取过 | 压力较大 |
| 🔴 危险 | 工具调用 > 20 次，连续读取大文件，历史对话很长 | 即将触及限制 |

### 压力响应策略

```
上下文压力评估
    │
    ├── 🟢 低压力 → 正常执行，无需调整
    │
    ├── 🟡 中压力 → 启动成本意识：
    │   - 避免 read_file 全文件读取，用 limit/offset
    │   - 避免 search_content 全局搜索，缩小 path 范围
    │   - 优先使用 code-explorer 子智能体探索代码
    │   - 工具调用结果只保留关键信息，不全文引用
    │
    ├── 🟠 高压力 → 主动减压：
    │   - 暂停非核心分支，聚焦当前主任务
    │   - 将探索性工作卸载给子智能体
    │   - 在输出中精简格式（表格代替长列表）
    │   - 主动向用户建议阶段性压缩
    │
    └── 🔴 危险 → 紧急模式：
        - 停止所有探索性读取
        - 只执行必要的文件修改
        - 强烈建议用户执行 /compact
        - 将当前状态摘要写入记忆文件，防止上下文断裂后丢失信息
```

### 大文件保护规则

| 场景 | 规则 | 原因 |
|------|------|------|
| SKILL.md > 400 行 | 只读 frontmatter + 核心流程区 | 避免 Skill 加载撑爆上下文 |
| 日志文件 > 200 行 | 只读最近 50 行 + 搜索关键词 | 历史日志不需要全量 |
| JSON 索引文件 | 正常读取（通常 < 5KB） | 设计上已经轻量化 |
| Python 源码 > 300 行 | 用 search_content 定位，不全文读取 | 只需要相关函数 |
| Markdown 报告 > 200 行 | 只读目录 + 目标章节 | 按需读取 |

### Skill 加载成本控制

| 并发 Skill 加载 | 成本 | 建议 |
|---------------|------|------|
| 0 个 | 最低 | 简单任务 |
| 1 个 | 低 | 正常任务 |
| 2 个 | 中 | 复杂任务，注意上下文预算 |
| 3+ 个 | 🔴 高 | 避免同时加载超过 2 个 Skill |

**规则**：如果已经加载了 2 个 Skill 且上下文压力为 🟠，不再主动加载第三个。
改为：从中提取必要信息 → 用子智能体完成需要该 Skill 的子任务。

## 🎯 核心理念

> **策略优于默认**。不是等上下文满了自动压缩，而是**阶段感知**——
> 在任务阶段的转换点主动压缩，在实现中途绝不让上下文被吃掉。

## 📊 任务阶段识别

```
┌─────────┐    ┌─────────┐    ┌─────────┐    ┌─────────┐    ┌─────────┐
│  研究    │───▶│  规划    │───▶│  实现    │───▶│  测试    │───▶│  交付    │
│Research │    │  Plan   │    │ Implement│    │  Test   │    │ Deliver │
└─────────┘    └─────────┘    └─────────┘    └─────────┘    └─────────┘
```

### 阶段判定信号

| 阶段 | 触发信号 | 典型行为 |
|------|---------|---------|
| **研究** | read_file 多次、search_content、web_search | 大量读取和分析 |
| **规划** | todo_write、方案讨论、"怎么做" | 产生结构化计划 |
| **实现** | write_to_file、replace_in_file、代码生成 | 写代码、改文件 |
| **测试** | execute_command 运行测试、调试 | 反复试错循环 |
| **交付** | open_result_view、deliver_attachments | 输出最终结果 |

## ✅ 应该压缩的时机

### 绿灯：推荐压缩

| 时机 | 原因 | 压缩策略 |
|------|------|---------|
| 研究 → 规划 转换时 | 研究过程冗长，规划需要的是结论 | 保留研究结论，丢弃搜索过程 |
| 调试 → 新功能 转换时 | 调试死胡同清理，新起点 | 保留调试结论（bug 原因），丢弃推理过程 |
| 子智能体返回后 | 子智能体读取了 20+ 文件 | 子智能体只返回摘要，不回传原始文件内容 |
| 复杂任务中间里程碑 | 长任务需要阶段性清理 | 保留已完成步骤的结论，丢弃实现细节 |
| 连续 5 次以上 read_file | 可能在重复读取同一批文件 | 做摘要后停止重复读取 |

### 黄灯：谨慎压缩（带条件）

| 时机 | 条件 | 压缩策略 |
|------|------|---------|
| 实现 → 测试 转换时 | 如果测试关联刚实现的代码 | 保留文件路径、函数名、变量名 |
| 多文件修改后 | 如果后续还需修改同一批文件 | 保留完整文件路径列表 |

---

## ❌ 绝不能压缩的时机

### 红灯：禁止压缩

| 时机 | 原因 | 丢失后果 |
|------|------|---------|
| **实现代码中途** | 变量名、函数签名、路径丢失 = 灾难 | 无法继续编码，需要重新读取所有文件 |
| **调试中途** | 推理链断裂 = 重新开始 | 之前的试错全部白费 |
| **子智能体刚返回结果** | 结果还没处理 | 需要重新调用子智能体 |
| **用户正在等待关键决策** | 决策依据丢失 | 无法做出正确判断 |
| **文件正在被编辑** | 编辑上下文断裂 | 可能产生错误的代码修改 |

## 📝 压缩指令模板

压缩时**必须带摘要指令**，不要空白压缩：

### 好的压缩（带指令）
```
/compact 保留以下关键信息：
1. 所有 API 端点路径和参数格式
2. 数据库 schema（表名、字段名、类型）
3. 已完成的文件修改列表
4. 用户明确要求的约束条件
```

### 坏的压缩（空白）
```
/compact          # ❌ 会丢失所有上下文
```

### 按阶段的压缩指令
```
# 研究阶段结束后
/compact 研究结论：{项目使用 FastAPI + PostgreSQL，认证用 JWT，前端 React + Tailwind}
                   丢弃所有搜索过程和中间 read_file 内容

# 实现阶段中途被迫压缩
/compact 保留：1. 当前正在编辑的文件路径 2. 已定义的函数签名 3. 未完成的 TODO 列表
              丢弃：已成功完成的文件修改细节

# 调试结束后
/compact 调试结论：{bug 原因是 xxx，修复方式是 yyy}
                   丢弃：所有试错过程和错误日志
```

## 🔄 自动压缩触发规则

以下情况 Agent 应**主动建议**用户压缩上下文：

| 触发条件 | 建议 |
|---------|------|
| 同一文件被 read_file ≥ 3 次 | "我反复读取了 {文件名}，建议压缩后继续" |
| 已完成 ≥ 5 个 todo 项 | "已大量完成工作，建议阶段压缩" |
| 阶段转换信号出现 | "研究阶段结束，建议压缩研究过程进入实现" |
| 对话中包含 ≥ 10 次工具调用 | "上下文较重，建议选择性压缩" |

## ⚙️ 核心规则

1. **阶段优先于计数**：不要只看 token 数量，要看任务阶段
2. **实现中途零压缩**：宁可多读文件，不在编码中途丢上下文
3. **带指令压缩**：永远告诉系统"保留什么"，不要空白压缩
4. **结论优于过程**：保留决策和结论，丢弃搜索和试错过程
5. **路径不可丢**：文件路径、函数签名、变量名是实现的生命线

## 🔍 Search Before Building（强制步骤）

在执行上下文压缩前，执行三层检查：

**Layer 1 - 项目内搜索**：
```bash
# 检查是否已有压缩记录
cat .workbuddy/memory/*.md 2>/dev/null | grep -i "压缩\|compact"
# 检查今日日志中的关键上下文
cat .workbuddy/memory/$(date +%Y-%m-%d).md 2>/dev/null | tail -50
# 检查是否有关键文件路径需要保留
grep -r "filePath\|file_path" .workbuddy/memory/ 2>/dev/null | head -10
```

**Layer 2 - 查找现有方案**：
- 检查 strategic-compact 自身是否已有相关场景的压缩模板
- 检查 workflow-loop 是否有该场景的标准压缩指令
- 查看其他 skill 是否有可复用的压缩模式

**Layer 3 - 如无现有方案**：
- 根据当前任务阶段确定压缩优先级
- 设计本次压缩的"保留/丢弃"清单
- 确认压缩时机是否合适（避免实现中途）

## 🚨 Escalation Rules（升级机制）

**必须立即 STOP 并升级的情况**：

| 触发条件 | 处理方式 |
|---------|---------|
| 用户正在等待关键决策结果 | STOP，等待用户决策后再考虑压缩 |
| 压缩可能导致文件编辑冲突 | STOP，确认所有编辑完成后再压缩 |
| 连续3次压缩均失败或被用户拒绝 | STOP，报告原因 |
| 用户要求保留的信息无法结构化 | STOP，建议保留完整上下文 |

**Escalation 格式**：
```markdown
STATUS: BLOCKED | NEEDS_CONTEXT
REASON: [问题描述]
CURRENT_PHASE: [研究/规划/实现/测试/交付]
ATTEMPTED: [尝试了什么]
RECOMMENDATION: [建议用户做什么]
```

## 📦 Workflow Loop（工作流闭环）

### 上游：上下文可能过重时触发

| 上游场景 | 触发时机 |
|---------|---------|
| 工具调用次数 ≥ 10 | 建议评估是否需要压缩 |
| 阶段转换点 | 研究→规划、规划→实现、实现→测试 等 |
| 子智能体返回后 | 主动建议压缩子智能体结果 |
| 长任务中间里程碑 | 阶段性总结后压缩 |

### 下游：压缩完成后

| 下游 skill | 联动方式 |
|-----------|---------|
| `workflow-loop` | 如果需要进入新工作流，触发对应闭环 |
| `self-improvement` | 记录压缩决策的踩坑经验 |
| `memory-consolidation` | 如果压缩产生重要结论，持久化到记忆 |

### 上下文压缩标准闭环
```
任务进行 → 监控上下文量 → 检测压缩时机 → 执行压缩 → 验证压缩质量
                                                    ↓
                                              压缩过重 → 回滚 → 重新压缩
                                                    ↓
                                              压缩合适 → 继续任务
```

## ✅ Completion Protocol（完成状态协议）

| 状态 | 含义 | 场景 |
|------|------|------|
| **DONE** | 压缩成功执行 | 上下文成功压缩且保留关键信息 |
| **DONE_WITH_CONCERNS** | 压缩完成但有风险 | 可能在实现中途压缩/部分信息可能丢失 |
| **BLOCKED** | 无法压缩 | 用户拒绝/时机不合适/无法结构化 |
| **NEEDS_CONTEXT** | 缺少压缩依据 | 需要用户明确要保留什么 |

### 压缩完成报告
```markdown
## 上下文压缩报告

STATUS: DONE

**压缩时机**：{阶段/触发条件}
**压缩前上下文**：约 {N} 轮对话
**压缩后上下文**：约 {N} 轮对话
**压缩率**：{X}%

### 保留的关键信息
- {保留的项目 1}
- {保留的项目 2}

### 丢弃的内容
- {丢弃的项目 1}
- {丢弃的项目 2}

**建议**：{后续是否需要进一步压缩}
```

## 🔄 触发词自进化规则

当用户输入某种表述但本 Skill 未被自动激活时，完成任务后**必须**执行：
1. 分析用户原始请求中的关键表述
2. 将其抽象为通用触发词（避免过于具体的个例）
3. 用 replace_in_file 工具将触发词追加到本文件 YAML frontmatter `description` 字段末尾
4. 不得重复添加已存在的触发词
