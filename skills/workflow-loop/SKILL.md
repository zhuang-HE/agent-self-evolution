# Workflow Loop - 标准工作流闭环模板库

## 🎯 技能定位

提供四种经过验证的标准工作流闭环，每个闭环都内置了：
- **Search Before Building**（三层搜索）
- **Completion Protocol**（完成状态协议）
- **Escalation Rules**（升级机制）
- **上下游关系**（与其他 skill 的联动）
- **Skill 注册表自省**（v1.2 新增，借鉴 Hermes 工具自省）
- **Skill 精简加载**（v1.3 新增，按需加载 Skill 内容，控制上下文消耗）

## 🔍 Skill 注册表自省（v1.2 新增）

> **借鉴 Hermes 工具自省能力**：在任务开始前快速扫描"我能做什么"，
> 而不是等用户说到触发词才想起来。

### 自省数据源

```
.workbuddy/memory/skill-registry.json
```

### 自省流程

```
收到用户请求
    ↓
Step 1: 读取 skill-registry.json 的 categories 结构（极低成本）
    ↓
Step 2: 匹配用户请求关键词与各 Skill 的 trigger_keywords + capabilities
    ↓
Step 3: 排序匹配结果
    - 精确匹配 trigger_keywords → 优先级高
    - 关键词匹配 capabilities → 优先级中
    - 类别匹配 → 优先级低
    ↓
Step 4: 决策
    - 匹配到 Skill → 预加载（与 self-improvement 意图预判协同）
    - 匹配到多个 Skill → 选择最精确的，其余标记为备选联动
    - 无匹配 → 正常执行，后续可用 find-skills 搜索外部 Skill
```

### 自省示例

```
用户说："帮我写个保险产品的条款"

skill-registry.json 自省结果：
1. non-motor-insurance-product
   - trigger_keywords 命中: "保险产品开发", "保险条款" ✅
   - capabilities: "条款撰写", "精算定价"
   → 预加载此 Skill

2. documentation（备选联动）
   - capabilities 匹配: "文档生成"
   → 条款写完后可能需要生成文档
```

### 注册表维护

| 触发时机 | 维护动作 |
|---------|---------|
| 安装新 Skill 后 | 在注册表中添加条目 |
| 卸载/删除 Skill 后 | 从注册表中移除 |
| Skill 版本升级后 | 更新 version 字段 |
| Skill 触发词变更后 | 更新 trigger_keywords |
| skill-evolution 审计时 | 验证注册表与实际 Skill 的一致性 |

## 🪶 Skill 精简加载（v1.3 新增）

> **问题**：加载 2-3 个 Skill 后，大量 reference 文件和示例代码会迅速消耗上下文。
> **方案**：Skill 加载时只注入核心流程，reference 文件按需读取。

### 加载成本分级

每个 Skill 加载到上下文时，根据内容结构分级读取：

| 级别 | 读取内容 | 预估成本 | 使用场景 |
|------|---------|---------|---------|
| **L0 摘要** | YAML frontmatter（name + version + description） | ~100 tokens | 判断是否需要此 Skill |
| **L1 核心** | YAML + 🎯 技能定位 + 📋 工作流程 | ~800 tokens | 执行 Skill 的主要流程 |
| **L2 标准** | L1 + 联动规则 + Escalation + Completion Protocol | ~2000 tokens | 复杂任务，需要完整的错误处理 |
| **L3 全量** | 整个 SKILL.md + references/ | ~5000+ tokens | 极少使用，仅在深度调试时 |

### 按压力选择级别

```
上下文压力评估（与 strategic-compact v1.2 协同）
    │
    ├── 🟢 低压力 → 加载 L2（标准，确保完整流程）
    │
    ├── 🟡 中压力 → 加载 L1（核心，足够执行主要流程）
    │   - 联动规则从 skill-registry.json 的 auto_triggers_after 获取
    │   - Escalation 规则按需查看
    │
    ├── 🟠 高压力 → 加载 L1（核心），且：
    │   - 不主动加载第二个 Skill
    │   - 需要的信息用子智能体获取
    │   - 非核心功能（示例、模板）跳过
    │
    └── 🔴 危险 → 加载 L0（摘要）：
        - 只知道"有这个 Skill"
        - 需要时用子智能体在独立上下文中加载和执行
        - 立即建议用户压缩
```

### 大 Skill 的精简策略

| Skill | 行数 | 精简建议 |
|-------|------|---------|
| workflow-loop | ~660 行 | 核心：闭环清单 + 强制联动矩阵；跳过：示例、详细步骤模板 |
| self-improvement | ~300+ 行 | 核心：触发标准 + 自动创建流程 + 模式检测；跳过：模板细节 |
| skill-evolution | ~400+ 行 | 核心：Phase 1-3 流程；跳过：报告格式模板、标准模板 |
| strategic-compact | ~400+ 行 | 核心：阶段识别 + 压缩时机 + 压力感知；跳过：详细模板 |
| code-review | ~200 行 | 标准加载，不算大 |

### 与注册表自省的协同

```
任务开始
    ↓
Step 1: skill-registry.json 自省（L0 摘要级）→ 匹配到 N 个候选 Skill
    ↓
Step 2: 评估上下文压力
    ↓
Step 3: 决定加载策略
    - 候选 1（最匹配）→ L1 或 L2 加载
    - 候选 2+（备选）→ 不加载，记住名字，需要时再加载
    - 候选 N（联动）→ 从 auto_triggers_after 获取触发关系，不预加载
```

## ⚡ 工具调用并行优化（v1.1 新增）

> **核心理念**：在任务开始时规划所有需要的调用，一次性并行发出无依赖的调用，减少往返等待。

### 执行前规划（强制步骤）

在开始任何非平凡任务之前，花几秒钟列出执行计划：

```
1. 明确任务目标
2. 列出所有需要读取的文件 / 需要调用的 API / 需要执行的命令
3. 分析依赖关系：
   - 哪些调用互相独立？→ 并行发出
   - 哪些调用依赖前一步结果？→ 串行等待
4. 第一轮调用：一次性发出所有无依赖的调用
5. 后续轮次：根据前一轮结果决定下一步
```

### 并行调用原则

| 原则 | 说明 | 示例 |
|------|------|------|
| **批量读取** | 多个文件需要读取时，一个 turn 内并行发出 | 读 A.py + B.py + config.json 一起发出 |
| **搜索合并** | 多个搜索可以并行 | grep 模式 A + grep 模式 B 一起发出 |
| **独立执行** | 多个命令互不依赖时并行 | `python test_a.py` + `python test_b.py` 一起发出 |
| **依赖串行** | 必须等前一步结果才能决定下一步 | 先 `read_file(A)` 决定是否需要 `read_file(B)` |

### 反模式（避免）

- ❌ 串行读 3 个无关文件：读 A → 等结果 → 读 B → 等结果 → 读 C
- ✅ 并行读 3 个无关文件：读 A + 读 B + 读 C 同时发出

- ❌ 串行搜两个无关关键词：grep X → 等结果 → grep Y
- ✅ 并行搜两个关键词：grep X + grep Y 同时发出

### 批次大小控制

| 批次 | 建议最大并行数 | 原因 |
|------|-------------|------|
| 第 1 批（信息收集） | 5-10 个调用 | 尽快获取全貌 |
| 后续批次（实现） | 3-5 个调用 | 需要仔细检查结果 |
| 最终批次（验证） | 1-3 个调用 | 需要精确控制 |

## 闭环1：🐛 Bug修复

```
investigate → root_cause → fix → verify → commit
```

### 流程图

```
用户报告 Bug
     ↓
┌─────────────────────────────────────────┐
│  Step 1: Search Before Building         │
│  Layer 1: 项目内搜索类似问题             │
│  Layer 2: find-skills 查找解决方案      │
│  Layer 3: 第一性原理分析根因            │
└─────────────────────────────────────────┘
     ↓
┌─────────────────────────────────────────┐
│  Step 2: 根因调查 (investigate)         │
│  - 重现问题                             │
│  - 追踪数据流                           │
│  - 定位问题代码                         │
└─────────────────────────────────────────┘
     ↓
┌─────────────────────────────────────────┐
│  Step 3: 修复实施                       │
│  - 实施修复                             │
│  - 编写/更新测试防止回归                │
└─────────────────────────────────────────┘
     ↓
┌─────────────────────────────────────────┐
│  Step 4: 验证 + 提交                   │
│  - 验证修复有效                         │
│  - Git commit + 描述                    │
└─────────────────────────────────────────┘
     ↓
✅ DONE
```

### 详细步骤

#### Step 1 · Search Before Building（强制）
```bash
# Layer 1 - 项目内搜索
grep -r "错误信息\|错误类型" --include="*.log" --include="*.md" .
cat .workbuddy/memory/*.md | grep -i "bug\|问题"

# Layer 2 - 查找现成方案
use_skill: find-skills
# 关键词：debug, investigate, error handling

# Layer 3 - 第一性原理
# 问题出在哪里？数据流追踪？
```

#### Step 2 · 根因调查
```markdown
## 根因分析

**问题描述**：[用户看到的问题]
**期望行为**：[应该怎样]
**实际行为**：[实际怎样]

**根因**：[找到的根本原因]

**修复方案**：[最简单的修复方式]
```

#### Step 3 · Escalation Rules
| 触发条件 | 处理 |
|---------|------|
| 3次尝试无法重现 | STOP，标记"无法重现"，要求更多信息 |
| 涉及多个模块 | STOP，拆分问题 |
| 需要改架构 | STOP，升级为功能开发闭环 |

#### Step 4 · 输出格式
```markdown
## Bug修复报告

STATUS: DONE

**问题**：{简要描述}
**根因**：{找到的原因}
**修复**：{做了什么}
**验证**：{如何确认修复有效}
**测试**：{添加了什么测试}
```

## 📊 Completion Protocol

所有闭环完成后必须报告状态：

| 状态 | 含义 |
|------|------|
| **DONE** | 所有步骤完成，目标达成 |
| **DONE_WITH_CONCERNS** | 完成但有遗留问题，用户需知 |
| **BLOCKED** | 无法继续，阻塞原因明确 |
| **NEEDS_CONTEXT** | 缺少信息，需要用户提供 |

## 🔗 Skill 强制联动规则（v1.1 新增）

> **核心理念**：关键任务路径上的 Skill 必须自动联动，不再依赖用户手动触发或触发词匹配。

### 强制联动矩阵

| 前置任务完成后 | 必须触发的联动 | 判断标准 | 联动方式 |
|--------------|--------------|---------|---------|
| **代码实现完成**（write_to_file / replace_in_file 修改了 .py/.ts/.js/.java 等） | `code-review` | 修改了 ≥ 3 个文件，或修改了核心逻辑文件 | 自动建议审查："代码已修改，需要 code-review 吗？" |
| **Skill 调用 ≥ 2 次重试后成功** | `self-improvement` 踩坑记录 | 同一个 API/工具/流程失败了 ≥ 2 次 | 会话结束前自动追加踩坑经验，不等审计 |
| **完成 ≥ 5 步的复杂任务** | `self-improvement` Skill 候选 | 任务含 ≥ 3 个可复用步骤 | 自动生成 Skill 候选建议 |
| **git push 成功** | `self-improvement` 经验记录 | 推送了非平凡代码 | 评估是否有值得记录的经验 |
| **功能开发闭环完成** | `code-review` + `self-improvement` | 闭环2完成 | 先审查，再自检 |
| **Bug修复闭环完成** | `self-improvement` 踩坑记录 | 闭环1完成 | 记录根因和修复方案 |
| **用户触发词未命中 Skill** | `skill-evolution` | 任务完成后发现本应加载的 Skill 未加载 | 自动追加触发词 |
| **工作记忆文件 > 30 天** | `memory-consolidation` | 日志文件过期 | 建议整理压缩 |

### 联动执行方式

```
强制联动 ≠ 强制执行

等级 1 - 自动执行（无需用户确认）：
  - 踩坑经验即时追加
  - 触发词盲区补充
  - 工作记忆写入

等级 2 - 自动建议（需要用户确认）：
  - "代码已修改，需要 code-review 吗？"
  - "这个流程可以封装为 Skill，要创建吗？"
  - "工作记忆中有 30 天前的日志，需要整理吗？"

等级 3 - 条件触发（满足条件时静默执行）：
  - git push 后的经验记录（用户无感）
  - 记忆系统的日常维护
```

### 联动防重复

- 同一会话内，同一联动规则最多触发 1 次
- 用户拒绝过的联动建议，本次会话不再重复建议
- 联动建议用一句话，不展开长篇说明
