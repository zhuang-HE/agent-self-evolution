# Self-Improvement - Agent 自我优化

## 🎯 技能定位

通过对当前会话和历史记忆的系统性反思，识别 Agent 的执行盲点、低效模式和改进机会，
将洞察持久化到工作记忆，形成持续进化的闭环。

---

## 🧠 自我优化的四个维度

### 维度 1：执行质量反思
- **多次尝试**：本次会话是否出现多次重试才成功的情况？为什么？
- **工具选择**：是否有更合适的工具但没有使用？
- **效率损耗**：哪些步骤是冗余的，下次可以跳过？
- **错误模式**：是否重复犯了相同类型的错误？

### 维度 2：用户理解深化
- **偏好识别**：用户是否展现了新的偏好或工作风格？
- **隐性需求**：用户说的和真正想要的是否一致？如何更好地识别隐性需求？
- **沟通摩擦**：哪些地方产生了误解？原因是什么？
- **反馈信号**：用户的哪些反应说明了满意或不满意？

### 维度 3：知识漏洞识别
- **Skill 缺失**：本次任务中是否有某种能力被反复重建，应该封装为 Skill？
- **触发词盲区**：哪些用户表述没有激活对应 Skill？
- **领域知识不足**：哪些领域知识需要补充到 references/ 中？
- **踩坑积累**：哪些错误应该记录到 Skill 的踩坑经验区？

### 维度 4：记忆系统优化
- **记忆写入**：今天的实质性工作是否都已写入工作记忆？
- **记忆质量**：已有记忆是否需要更新或纠正？
- **记忆健康**：工作记忆文件是否需要整理压缩？

## 🔮 意图预判层（v2.1 新增）

> **核心理念**：从被动响应触发词 → 主动预判用户意图，提前加载最优 Skill。

### 触发时机
每次收到用户请求时，在开始执行之前，执行意图预判（< 3 秒内完成，不展开 Skill 全文）。

### 预判流程

```
收到用户请求
    ↓
扫描所有 Skill 的 name + description（仅标题行，不加载全文）
    ↓
判断：是否有 ≥ 1 个 Skill 能显著提升任务效率？
    │
    ├── 有 → 预加载该 Skill（即使触发词未精确命中）
    │       预加载优先级：
    │       1. 任务类型精确匹配（如金融数据 → finance-data-retrieval）
    │       2. 领域相关匹配（如股票分析 → stock-analyst）
    │       3. 工具链匹配（如写代码 → code-review 准备联动）
    │
    └── 无 → 正常执行，不做多余加载
    ↓
执行过程中如果发现效率低下 → 中途补充加载 Skill
```

### 预判示例

| 用户说 | 触发词匹配 | 意图预判 | 应该加载 |
|--------|-----------|---------|---------|
| "帮我拉一下利润表" | 可能没命中 | 金融数据检索 | `finance-data-retrieval` |
| "这个代码帮我看看" | 可能没命中 | 代码审查 | `code-review` |
| "推送到 GitHub" | `git-workflow` | Git 操作 | `git-workflow` |
| "做个调研" | `web-research` | 研究任务 | `web-research` + `Deep Research` |
| "帮我记一下" | 可能没命中 | 知识管理 | `腾讯ima` 或记忆写入 |

### 反模式（不要过度预判）
- ❌ 用户说"你好"→ 不预判加载任何 Skill
- ❌ 简单的文件读取请求 → 不预判加载重型 Skill
- ❌ 不确定的领域 → 先执行，观察后再决定

## 📋 工作流程

### Step 0 · 意图预判（新增）
```
0. 快速扫描 Skill 列表，判断是否有匹配 Skill
   0a. 如果有 → 预加载该 Skill
   0b. 如果没有 → 进入 Step 1
```

### Step 1 · 读取上下文
```
1. read_file 读取 .workbuddy/memory/MEMORY.md（长期记忆）
2. read_file 读取今日 .workbuddy/memory/YYYY-MM-DD.md（短期日志）
3. 回顾当前会话的完整交互（无需读文件，直接从上下文获取）
```

### Step 2 · 系统反思
```
按四个维度逐一反思，形成结构化的"自我评估报告"：
- 本次做得好的地方（强化）
- 本次做得不够好的地方（改进）
- 发现的新模式或新知识（积累）
- 下次应该不同做的事情（行动）
```

### Step 3 · 持久化改进
```
根据反思结果，执行以下持久化动作：

① 更新工作记忆
   - 将新发现的用户偏好写入 MEMORY.md
   - 将今日未记录的实质性工作追加到日志

② 更新 Skill 触发词
   - 如发现触发词盲区，调用 skill-evolution 能力更新对应 Skill

③ 添加踩坑经验
   - 如发现反复出现的错误，追加到对应 Skill 的踩坑经验区

④ 创建新 Skill（可选）
   - 如发现需要封装为 Skill 的能力，标记出来供用户决策
```

### Step 4 · 生成报告
```
生成简洁的自我优化报告，向用户呈现：
- 本次改进了什么
- 下次交互将有什么不同
- 建议用户做什么（如创建新 Skill）
```

### Step 5 · 质量评分（v2.3 新增）

> **借鉴 Hermes 的执行质量度量**：没有度量就没有改进。
> 每次自我优化时，给本次会话的执行质量打分，追踪历史趋势。

#### 评分维度

| 维度 | 权重 | 评分标准（1-5 分） |
|------|------|-------------------|
| **目标达成** | 30% | 1=未完成 3=部分完成 5=完全达成 |
| **效率** | 25% | 1=严重超支 3=符合预算 5=优于预算 |
| **工具选择** | 15% | 1=多次选错 3=基本正确 5=最优选择 |
| **用户理解** | 15% | 1=多次误解 3=基本理解 5=精准理解 |
| **知识复用** | 15% | 1=重复造轮子 3=部分复用 5=充分利用已有 Skill/记忆 |

#### 计算方式

```
总分 = Σ(维度分 × 权重) → 1.0 - 5.0

质量等级：
  ≥ 4.5 → ⭐⭐⭐⭐⭐ 优秀（可作为 Skill 创建的输入）
  ≥ 3.5 → ⭐⭐⭐⭐ 良好（正常水平）
  ≥ 2.5 → ⭐⭐⭐ 合格（有改进空间）
  < 2.5 → ⭐⭐ 需反思（必须触发深度改进分析）
```

#### 评分持久化

将评分写入 memory-index.json 的 `quality_history`：

```json
{
  "quality_history": [
    {
      "date": "2026-04-25",
      "session_type": "功能开发",
      "scores": {
        "goal": 5, "efficiency": 4, "tools": 4, "understanding": 5, "reuse": 3
      },
      "total": 4.35,
      "grade": "⭐⭐⭐⭐",
      "key_improvement": "可以更多利用子智能体卸载探索性工作"
    }
  ]
}
```

#### 趋势分析

| 模式 | 含义 | 行动 |
|------|------|------|
| 连续 3 次 ≥ 4.0 | 稳定高质量 | 当前 Skill/工作流有效，维持 |
| 连续 2 次下降 ≥ 0.5 | 质量下滑 | 触发深度反思：是什么变了？ |
| 特定维度持续 ≤ 3 | 系统性短板 | 针对该维度创建改进 Skill 或更新规则 |
| 总分波动大（极差 ≥ 2） | 不稳定 | 可能与任务类型/上下文压力相关，分析关联 |

## 🔄 自动触发机制

除用户主动调用外，以下情况**必须**自动触发自我优化（借鉴 Hermes Agent 的自动进化设计）：

| 触发场景 | 优化重点 | 最低阈值 |
|---------|---------|---------|
| 会话中出现 3 次以上重试 | 工具选择 + 踩坑经验记录 | 同一错误 ≥ 2 次 |
| 用户明确表达不满意 | 用户理解 + 沟通方式改进 | 任何负面反馈 |
| 完成一个复杂多步骤任务 | 工作流效率 + Skill 封装机会 | ≥ 5 个工具调用 |
| 用户分享了新的偏好或约束 | 立即写入 MEMORY.md | 任何新偏好 |
| **任务完成后自动 Skill 候选识别** | 从执行轨迹提取可复用模式 | 任务含 ≥ 3 个可复用步骤 |
| **跨会话模式识别** | 与 MEMORY.md 对比，发现重复模式 | 同类任务 ≥ 2 次会话出现 |

### 触发决策流程图（v2.4 新增）

```
任务/会话中的一个里程碑点
    ↓
检查触发条件（按优先级）
    │
    ├── 1. 用户明确说"反思/复盘/总结"
    │       → 立即执行完整反思流程（Step 0-5 + 质量评分）
    │
    ├── 2. 用户表达不满（"不对""重新来""不是这样的"）
    │       → 立即执行维度 2（用户理解）专项反思
    │       → 标记本次会话质量评分权重调整（用户理解维度权重临时 +50%）
    │
    ├── 3. 工具调用失败重试 ≥ 2 次（同一操作）
    │       → 记录踩坑经验到对应 Skill
    │       → 不执行完整反思（避免打断流程），在任务完成后一并反思
    │
    ├── 4. 任务阶段完成（工具调用累计 ≥ 5 次）
    │       → 快速自检：回顾已执行步骤，是否有冗余/可优化
    │       → 如果发现明显低效，立即调整后续策略
    │       → 不中断用户流程，静默优化
    │
    ├── 5. 任务全部完成
    │       → 执行完整反思流程（Step 1-4）
    │       → Skill 候选识别（如果 ≥ 3 个可复用步骤）
    │       → 质量评分（Step 5）
    │       → 写入日志 + 更新记忆
    │
    └── 6. 用户分享了新偏好/约束
            → 立即写入 MEMORY.md（带置信度）
            → 不执行完整反思
```

### 触发条件的工具调用计数规则（v2.4 新增）

> **问题**：原设计说"≥ 5 个工具调用"，但没定义什么是"一次工具调用"。

**计数规则**：

| 计数 | 算 1 次的工具调用 | 不计数 |
|------|------------------|--------|
| ✅ | read_file、write_to_file、replace_in_file、search_content、search_file、execute_command、list_dir | read_lints（诊断检查） |
| ✅ | use_skill（加载 Skill） | conversation_search（上下文检索） |
| ✅ | web_search、web_fetch | update_memory（记忆更新） |
| ✅ | task（子智能体派发，每派发 1 次计 1） | todo_write（任务管理） |
| ✅ | RAG_search | deliver_attachments（结果交付） |

**统计时机**：从会话的第一个工具调用开始累计，每次完成任务后重置计数器（开始新任务时不清零，继续累加——一个会话可能有多个任务）。

### 自动 Skill 候选识别（借鉴 Hermes 自动创建 Skill）

在完成复杂任务后，自动判断是否应该创建/建议 Skill：

```
判断标准（满足任一即触发）：
1. 任务包含 ≥ 3 个可复用的步骤序列
2. 本次任务的解决路径在 MEMORY.md 中没有记录
3. 用户之前手动执行过类似任务（跨会话模式）
4. 任务涉及特定的领域知识或 API 调用模式

输出格式：
- [Skill 候选] {候选名称}：{一句话描述} + {触发步骤摘要}
- 提交给用户确认是否创建正式 Skill
```

### Skill 自动创建 MVP 流程（v2.2 新增）

> **借鉴 Hermes 核心能力**：从执行轨迹自动提取可复用模式，生成 SKILL.md 模板。

#### 创建条件（必须满足 ≥ 2 条）

| 条件 | 说明 | 示例 |
|------|------|------|
| 步骤可复用 | 任务包含 ≥ 3 个有序步骤，可被不同输入重复执行 | "读取配置→验证格式→写入数据库" |
| 领域专精 | 涉及特定领域知识、API 模式或工作流 | 保险产品定价流程、量化回测模板 |
| 跨会话重复 | 类似任务在 ≥ 2 次会话中出现 | "每次都要手动查 API 文档" |
| 现有 Skill 未覆盖 | 检查 Skill 注册表中无匹配项 | 没有任何 Skill 处理"合同审查" |

#### 自动创建流程

```
任务完成 → 触发 Skill 候选识别
    ↓
满足创建条件？
    ├── 否 → 跳过
    └── 是 → 执行以下步骤：
        ↓
Step 1: 提取模式
    - 从执行轨迹中提取：步骤序列、工具调用模式、关键参数、错误处理
    - 识别变量（哪些是每次不同的输入）、常量（哪些是固定的配置）

Step 2: 生成模板
    - 使用标准 SKILL.md 模板（见下方）
    - 自动填充：name、description（含触发词）、工作流程、踩坑经验模板
    - 占位符标记不确定的部分（用 TODO: 注释）

Step 3: 用户审核
    - 向用户展示：Skill 名称、描述、核心流程预览
    - 用户选择：✅ 创建 / ✏️ 修改后创建 / ❌ 放弃
    - 如果用户选择创建 → write_to_file 写入 ~/.workbuddy/skills/{name}/SKILL.md

Step 4: 注册
    - 将新 Skill 信息追加到 Skill 注册表（memory/skill-registry.json）
    - 更新 MEMORY.md 的 Skills 生态分区
```

## 📐 记忆写入规范

优先级从高到低：

```
1. 用户明确说"记住"的内容 → 立即写 MEMORY.md，置信度 [0.9]
2. 用户偏好（格式/风格/工具/语言）→ 写 MEMORY.md 对应分区，带置信度
3. 项目约定（命名规范/技术栈决策）→ 写 MEMORY.md 对应项目分区，置信度 [0.7]
4. 踩坑经验（多次试错才成功）→ 写对应 Skill 的踩坑区
5. 今日实质性工作 → 写当日 YYYY-MM-DD.md
```

不应写入记忆的内容：
- 临时搜索结果（非结论性的）
- 单次任务的中间过程
- 一次性的错误处理细节

## 📊 置信度评估规则（v2.0 核心）

### 写入时的置信度判定

| 场景 | 置信度 | 示例 |
|------|--------|------|
| 用户明确说"记住这个/记下来" | **[0.9]** | "记住，我用的是 Vue 3 不是 Vue 2" |
| 用户主动选择并强调 | **[0.7]** | "用 Tailwind，不要 Bootstrap" |
| 用户多次遵循同一模式（2-3次） | **[0.7]** | 连续 3 次选择 Plotly 而非 Matplotlib |
| 用户提及 1 次，未强调 | **[0.5]** | "这次用 Python 吧" |
| AI 观察到但用户未声明 | **[0.3]** | 每次都先读 README 再动手 |

### 写入格式
```markdown
- [0.9] **偏好描述**：具体内容
- [0.7] **工具选择**：Plotly 优于 Matplotlib（用于交互式图表）
- [0.3] **观察模式**：可能偏好函数式编程（待确认）
```

### 晋升与降级
- **晋升**：[0.3]→[0.5] 出现第 2 次，[0.5]→[0.7] 出现第 4 次，[0.7]→[0.9] 用户明确确认
- **降级**：30 天内未被引用或遵循，降一级；60 天仍未引用，标记为 `[已过期]`
- **冲突处理**：新信息与 [0.9] 条目冲突时，保留旧的并提示用户确认是否更新

## 🗂️ 项目隔离写入规则（v2.0 核心）

写入 MEMORY.md 时，必须判断条目属于哪个分区：

```
1. 判断条目是否跨项目通用
   - 是 → 写入 "🔧 通用偏好" 区
   - 否 → 识别所属项目名，写入对应 "📁 项目：{名}" 区

2. 识别项目名的方法（优先级）
   a. 当前工作区路径中的项目名
   b. 用户在对话中明确提及的项目名
   c. 文件路径、技术栈关键词推断

3. 如果目标项目分区不存在
   - 检查是否有相似度 > 80% 的分区（提示用户确认合并）
   - 否则创建新分区
```

## ⚙️ 核心规则

1. **诚实反思**：不美化执行质量，如实记录问题
2. **行动导向**：反思必须产出可执行的改进，不空谈
3. **最小改动**：每次只更新确定需要改变的内容，不大规模重写
4. **用户透明**：所有持久化改动在报告中明确列出
5. **可撤销**：所有改动均为追加，不删除已有内容（除非用户明确要求）

## 📦 Workflow Loop（工作流闭环）

### 上游：所有 skill
- 每个 skill 完成后**必须**自动触发自我优化（不再仅建议）
- 特别是复杂多步骤任务完成后

### 下游：skill-evolution
- 识别到 skill 需要更新时 → 触发 skill-evolution
- 识别到需要新 skill 时 → 触发 skill-creator

### 关键路径（强化版：借鉴 Hermes 自进化闭环）
```
用户请求 → 执行 skill → 完成后强制自检（self-improvement）
                         ↓
                    ├── 发现改进点 → 持久化（MEMORY.md / Skill 踩坑区）
                    ├── 发现可复用模式 → 建议 Skill 候选 → skill-creator
                    ├── 发现触发词盲区 → 触发 skill-evolution
                    └── 踩坑经验 ≥ 2 次 → 自动追加到对应 Skill
```

### 跨会话学习路径（借鉴 Hermes 跨会话记忆）
```
会话 N 执行任务 → 写入日志 → 提取经验 → 更新 MEMORY.md
                                              ↓
会话 N+1 开始 → 读取 MEMORY.md → 匹配当前任务 → 检测重复模式
                                              ↓
                                    发现模式 → 建议/直接使用已有 Skill
                                    无模式 → 正常执行 → 会话结束后自检
```

### 跨会话模式检测引擎（v2.2 新增）

> **借鉴 Hermes 的跨会话持续学习**：不是每次都从零开始，而是识别"又来了"的模式。

#### 检测时机

每次新会话开始、且需要读取工作记忆时自动执行。

#### 检测流程

```
新会话开始
    ↓
Step 1: 读取 memory-index.json（极低成本）
    ↓
Step 2: 匹配用户请求关键词与 cross_session_patterns
    ↓
Step 3: 判断结果
    │
    ├── 高匹配（≥ 2 个 pattern 命中，或频率 ≥ 5）
    │       ↓
    │   主动告知用户：
    │   "这个任务类型你做过 {N} 次了，上次是 {日期}。
    │    已有相关 Skill：{skill-name}，建议直接使用。
    │    上次的关键经验：{从踩坑经验提取}"
    │   → 预加载对应 Skill，跳过摸索阶段
    │
    ├── 中匹配（1 个 pattern 命中，频率 2-4）
    │       ↓
    │   静默预加载对应 Skill（不主动告知，但准备好）
    │
    └── 无匹配
            ↓
        正常执行
```

#### 模式记录规范

在 memory-index.json 的 `cross_session_patterns` 中维护：

```json
{
  "pattern": "量化数据查询",
  "frequency": 8,
  "last_seen": "2026-04-24",
  "suggested_skill": "finance-data-retrieval",
  "key_lessons": ["ts_code 必须带后缀", "频率参数格式有限制"]
}
```

| 字段 | 说明 | 更新时机 |
|------|------|---------|
| `pattern` | 模式名称 | 首次识别时创建 |
| `frequency` | 出现次数 | 每次匹配时 +1 |
| `last_seen` | 最后出现日期 | 每次匹配时更新 |
| `suggested_skill` | 推荐的 Skill | 模式稳定后设定 |
| `key_lessons` | 关键经验摘要 | 从踩坑经验中提取 |

#### 模式衰减

- 30 天未出现的模式：frequency 减半
- 60 天未出现的模式：标记为 `[休眠]`，不再主动推荐
- 90 天未出现的模式：从索引中移除

## 🔄 触发词自进化规则

当用户输入某种表述但本 Skill 未被自动激活时，完成任务后**必须**执行：
1. 分析用户原始请求中的关键表述
2. 将其抽象为通用触发词（避免过于具体的个例）
3. 用 replace_in_file 工具将触发词追加到本文件 YAML frontmatter `description` 字段末尾
4. 不得重复添加已存在的触发词
